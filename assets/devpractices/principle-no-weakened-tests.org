#+title: Never Weaken a Test to Make It Pass
#+filetags: :principle:testing:devpractice:

A failing test that stands between a change and a green build should be treated as information about the change, not as an obstacle to the change. Loosening an assertion, adding a skip or an `xfail` marker, widening a numeric tolerance, or deleting the specific case that fails — done in order to get the suite passing rather than because the test was actually wrong — defeats the entire purpose a test exists to serve. A test exists to falsify the implementation: to assert, mechanically and repeatedly, that the system does what it is supposed to do, and to fail loudly the moment that stops being true. Weakening a test in response to a failure inverts this relationship — instead of the test constraining the implementation, the implementation's current (possibly broken) behavior is retroactively used to constrain the test.

The failure mode is subtle because each individual instance looks locally reasonable: a test is failing, there's schedule pressure, the failure looks like it might be a flaky timing issue or an overly strict tolerance, and it's faster to loosen the assertion than to investigate. Sometimes this judgment is even correct — some tolerances genuinely were too strict, some timing assumptions genuinely were flaky. The danger is that this judgment call, applied under time pressure and without a rigorous check on which failures are "the test was wrong" versus "the code regressed," systematically drifts toward the convenient answer. Over enough repetitions, the suite accumulates skipped tests, suspiciously wide tolerances, and assertions that were quietly narrowed to stop catching exactly the case that broke — a test suite that reports green while covering meaningfully less than it used to, with no record anywhere of what coverage was lost or why.

The corrective is to require an explicit, reviewed justification any time a test's assertion gets weaker rather than stronger, distinct from the general code-review process for the surrounding change: what specifically was wrong with the old assertion, and why is the new one still a meaningful falsification test rather than a tautology? A test changed to accommodate a regression should never be indistinguishable, in the review history, from a test genuinely fixed because it encoded a mistaken assumption. If a test is being skipped rather than fixed, the skip should carry a tracked reason and a tracked follow-up — see [[id:principle:no-deferred-bugs][no deferred bugs]] — not a silent `@skip` that quietly becomes permanent.

A useful gut check: if the fix for a failing test is to make the test more permissive, ask whether the same change could instead make the implementation more correct. Almost always, a test failure caused by a real behavior change should be resolved by either updating the test to assert the *new, deliberately intended* behavior (with that intent stated explicitly, not inferred from what happened to compile) or by fixing the implementation to match what the test already correctly expected — never by making the test unable to tell the difference between the two going forward.

This principle is inseparable from [[id:principle:tests-as-spec][tests as spec]] — a test that has been weakened to pass is no longer specifying anything — and from [[id:practice:adversarial-testing][adversarial testing]], since the entire discipline of writing tests that try to break the implementation is worthless if a failing adversarial test can simply be loosened away.

#+title: Tests as the Executable Specification
#+filetags: :principle:testing:devpractice:

Treat a test suite as the executable specification of what a system is supposed to do, not merely a record of what it happens to do today. This is a deliberate shift in how tests are written: instead of writing a test after the fact to confirm the code you already wrote behaves the way it currently behaves, write (or review) tests as statements of intended behavior — including the behavior at boundaries, error conditions, and branches that the happy-path implementation may not yet even handle correctly. A test suite built this way pins down what "correct" means for the system independently of any particular implementation, which is exactly what lets you refactor the implementation with confidence, or catch a regression the moment it's introduced rather than the moment a user reports it.

This means favoring intentional, branch-level coverage over incidental, line-level coverage. Line coverage answers "did the test suite execute this line at least once," which is a weak guarantee — a line can execute without any assertion checking that what it produced was correct, and a test that happens to walk through a branch without deliberately targeting the decision that branch represents proves nothing about whether the decision was made correctly. Branch-level, intent-driven coverage instead asks "for every meaningfully distinct decision this code makes, is there a test that specifically targets each outcome of that decision and asserts the behavior the spec requires for it" — including outcomes the current implementation gets wrong, if the goal is to catch that it's wrong rather than to celebrate that the wrong behavior is at least covered.

The failure mode when tests describe current behavior instead of intended behavior: a test suite reports high line coverage, giving the team false confidence, while actually encoding whatever the implementation happened to do at the moment the test was written — including its bugs. A later refactor that "breaks" one of these tests is ambiguous by construction: did the refactor introduce a regression, or did it fix a bug the test had accidentally enshrined as correct behavior? Nobody can tell from the test alone, because the test never stated what was *supposed* to happen, only what *did* happen once. This ambiguity is expensive precisely at the moment it matters most — during a refactor or a bug fix, when you most need the test suite to give an unambiguous verdict.

The corrective is to write tests from the specification or the intended contract, not from a trace of the current implementation's output — and where no written specification exists yet, use the act of writing the test as the forcing function to make the intended behavior explicit (which then belongs in a design document per [[id:principle:explicit-design-stances][explicit design stances]], not only in test code). For every function or component, ask "what are the meaningfully distinct cases this needs to handle correctly" rather than "what happens if I run this with the input I have handy" — the difference between deriving test cases from the problem domain versus deriving them from whatever's easy to construct is the difference between a spec and a snapshot.

This principle is what [[id:principle:no-weakened-tests][no weakened tests]] exists to protect — a test that specifies intended behavior is worthless the moment it's loosened to match whatever the implementation currently does — and it's the foundation [[id:practice:adversarial-testing][adversarial testing]] builds on, since adversarial test design is branch-level, intent-driven coverage specifically aimed at the failure and boundary branches a happy-path-only suite would never target.

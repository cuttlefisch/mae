#+title: Write Down Design Stances Explicitly
#+filetags: :principle:process:devpractice:

When a design or specification decision is made — a deliberate choice about how something should behave, what tradeoff was accepted, what a component is and isn't responsible for — write it down explicitly, in a comment, a decision record, or a design document, rather than leaving it implicit in the shape of the code. An implicit stance is invisible to everyone who didn't personally participate in the original discussion, which in practice means it's invisible to almost everyone who will ever touch the code afterward, including the original author a year later.

An implicit stance gets silently violated by the next change because nobody wrote it down. This is the concrete failure mode: a function was deliberately written to never retry a failed operation, because retries in that context could cause a duplicate side effect (a duplicate charge, a duplicate message send) — but that reasoning existed only in the original author's head, or in a chat conversation nobody thought to preserve. Months later, someone notices the function fails on transient errors and, reasonably, adds a retry loop to make it more resilient — reintroducing the exact duplicate-side-effect risk the original design deliberately avoided, because the constraint that made "just add a retry" wrong was never recorded anywhere the second person could have found it. The reviewer approves the change too, because the reviewer also has no way to know the constraint exists. The system regresses silently, and it's only caught later — if it's caught at all — when the duplicate side effect actually happens in production.

The corrective is cheap and specific: whenever you make a decision that isn't the "obvious" choice a competent engineer would make with no other context — whenever you're deliberately not doing the thing that looks like the natural next step — write down why, right where a future editor will see it. A comment directly above the code it constrains ("do not add retry logic here: X calls this with side effect Y, and retries would duplicate it") is often sufficient for a narrow, local stance. A stance that governs a whole subsystem or a cross-cutting concern belongs in a design document or decision record instead, so it's discoverable by someone who hasn't yet found the specific line of code it governs. Either way, the stance should be co-located with, or clearly cross-linked to, the code it constrains — a decision recorded only in a meeting transcript or a chat thread that nobody links from the code is barely more durable than not recording it at all.

This is not a call to over-document routine code — most code needs no such comment, because most code's behavior is exactly what it looks like it does. The discipline applies specifically to the cases where the code's behavior would be surprising, or where a reasonable future editor could plausibly "fix" it into something worse without realizing they'd violated a constraint. If you find yourself thinking "someone might reasonably try to change this, and if they do, it'll break something non-obvious," that's the signal to write the stance down now, while you still remember the reasoning, rather than relying on it surviving in institutional memory.

This principle underlies [[id:practice:caution-annotations][caution annotations]] as a concrete in-code mechanism for exactly this kind of landmine-flagging, and it connects to [[id:principle:bugs-are-drift-signals][bugs are drift signals]]: a bug caused by someone violating an undocumented stance is a drift bug whose root cause is specifically the absence of documentation, and the durable fix is writing the stance down at the point of the fix, not merely reverting the violation.

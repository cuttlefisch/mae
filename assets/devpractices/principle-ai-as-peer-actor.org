#+title: Treat an AI Collaborator as a Peer Actor, Not a Bolted-On Mode
#+filetags: :principle:ai-collaboration:devpractice:

When integrating an AI agent into a system that humans also operate, give it access to the same primitives and APIs the human uses, rather than building a parallel, separate "AI mode" with its own weaker or differently-shaped interface. The distinction matters structurally: a peer actor calls the identical functions, sees the identical state, and is subject to the identical invariants as a human user. A bolted-on mode, by contrast, tends to accrete its own simulation layer — synthesized keystrokes, a shadow API surface, special-cased code paths that only run "when the AI is driving" — which is both more code to maintain and a source of behavioral divergence between what the AI experiences and what a human experiences.

The failure mode when this principle is ignored: a team adds AI capability to an existing tool by wrapping the tool's UI-level actions (simulated clicks, synthesized key events, screen-scraping output) instead of exposing the tool's actual internal API to the agent. This works at first, for the narrow set of behaviors that were tested. Then the underlying UI changes shape slightly — a dialog gets reordered, a button is renamed, a timing assumption shifts — and the AI integration breaks silently, because it was never coupled to the real interface, only to an incidental surface representation of it. Meanwhile, features added to the "real" interface are invisible to the AI layer until someone remembers to update the shadow implementation, so the two surfaces drift further apart every release. The team ends up maintaining two products under one name.

The corrective is to expose one API surface and have both humans and the AI agent call into it — through direct function calls, a keybinding layer that resolves to the same commands the agent invokes, or a protocol (tool-calling, RPC) that is a thin, faithful mirror of the internal primitives rather than a reinterpretation of them. When a new capability is added for the human-facing surface, it should be automatically or trivially available to the agent, and vice versa, because there is structurally only one implementation to update. This also has a safety benefit: a peer-actor design makes it much easier to reason about what an AI agent can and cannot do, because its capabilities are exactly the set of primitives it has access to — the same set a human's permissions would be scoped by — rather than an ad hoc, hard-to-audit simulation layer with its own implicit capability boundary.

Treating the AI as a peer also changes how you think about state visibility: give the agent the same structured, semantic view of system state that a well-built human-facing tool would have (types, references, diagnostics, not just raw text), rather than forcing it to re-derive structure from an interface designed for visual human consumption. An agent parsing rendered pixels or scraped text to reconstruct what a native API call would have handed it directly is a symptom of the same underlying mistake — treating the agent as an outside consumer of the system rather than an actor operating it.

This principle is closely related to [[id:principle:no-hardcoding][no hardcoding]] and [[id:principle:single-source-shared-computation][single source for shared computation]]: an AI-specific shadow API is itself a form of duplicated, un-shared implementation, and it tends to accumulate the same hardcoded special-casing that duplicated logic always does. See [[id:workflow:ai-pairing-loop][the AI pairing loop]] for how this plays out in day-to-day collaborative workflows once the peer-actor API exists.

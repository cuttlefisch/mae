#+title: Design for Runtime Redefinability
#+filetags: :principle:architecture:devpractice:

A system designed to be modified while it is running — redefine a function, reload a module, patch a behavior — without a full restart dramatically shortens the iteration loop for both human and AI-driven development. This is the property that makes a live REPL or a hot-reload workflow possible at all: the difference between "change one function and observe the effect in the next few seconds" and "change one function, rebuild, restart, re-navigate to the state you were just in, then observe the effect" is not a minor convenience. It compounds across every single iteration of a development session, and a system that requires the second workflow pays that tax on every change, forever.

The value shows up most clearly in how it shapes behavior under uncertainty. When redefinition is cheap, the natural response to "I'm not sure this is right" is to try it and look — experiment, observe, adjust, repeat. When redefinition is expensive, the natural response to the same uncertainty is to reason longer in the abstract before committing to a change, because the cost of being wrong includes a full rebuild-and-restart cycle. Both debugging and AI-assisted iteration lean heavily on the fast loop: a debugging session is fundamentally a sequence of hypotheses tested against a running system, and an AI agent proposing and refining changes benefits from the same tight feedback cycle a human pairing partner would want — see the iterate step of [[id:workflow:ai-pairing-loop][the AI pairing loop]], which this property makes cheap rather than expensive.

The failure mode when this property is absent: a change that could be verified in seconds against a live, already-warmed-up system instead requires a full rebuild and restart, discarding all accumulated state — open connections, populated caches, a carefully reconstructed reproduction scenario — every time. Developers respond rationally to this cost by batching more changes together before testing, which means each restart now needs to isolate which of several simultaneous changes caused a given effect, which is slower and less certain than isolating one change at a time. Over a project's lifetime this discourages the small, frequent, well-isolated changes that are easiest to reason about and rewards large, infrequent, harder-to-debug ones — the opposite of what good iterative practice wants.

The tradeoff deserves an honest accounting: supporting live redefinition safely, without leaving the running system in an inconsistent state — stale closures still referencing an old version of a redefined function, partially-applied migrations, state that assumed the old code's invariants — is real engineering cost. It usually requires deliberate support in the runtime (a garbage collector or reference model that tolerates in-place redefinition, an explicit reload protocol, versioned state) rather than falling out for free. This is a deliberate design investment, not a free property, and it is worth making specifically for systems meant to be iterated on interactively and often — an editor, a REPL-driven language runtime, a configuration layer — rather than for every system unconditionally.

This principle compounds with [[id:principle:concurrency-safety-first][designing for concurrency from day one]]: redefining a function while its old version is still executing on another thread, or while shared state is being concurrently accessed, is strictly harder than redefining it under exclusive single-threaded access, and a system that hasn't already solved the concurrency problem will find the redefinition problem much harder to solve safely on top of it.

#+title: Local-First Design: the Local Path Is the Floor, Not the Fallback
#+filetags: :principle:architecture:devpractice:

Prefer a design where core functionality works fully offline, running entirely embedded within the user's own process, with any network service or central server treated as an optional accelerant rather than a bare requirement. A server earns its place in the architecture by providing something the local path structurally cannot: durability across sessions on a machine the user doesn't control, coordination between multiple independent peers who need to agree on shared state, or some other capability a single local process genuinely cannot offer on its own. It never earns its place by default, and it never earns its place simply because that's where the logic happened to get written first.

The test is a concrete question, not a vibe: before making a feature depend on a server or daemon, ask what specific thing the server provides that the local path could not. If the honest answer names a real capability — this server is the only place multiple peers can rendezvous to agree on a merge order; this server is the only thing that persists state past the lifetime of the local process — the dependency is earning its place and the design should say so explicitly. If the honest answer is "nothing in particular, it's just where we happened to put the logic," that is a direct signal the dependency is not earning its place and the feature should be reworked to run locally, with the server reintroduced later only for the specific piece of it that actually needs one.

The failure mode when this is ignored: a feature is built server-dependent from the start, not because the feature inherently needs a server but because a server process was already running for something else and it was the path of least resistance to put the new logic there too. Over time more features accrete the same way, each individually reasonable, until the local path is a degraded, second-class experience — a smaller feature set, or missing entirely — for any user who doesn't want to run extra infrastructure, doesn't have reliable network access, or simply wants the tool to work the moment it's installed. Nobody chose this outcome; it emerged from a long sequence of small conveniences that each shifted a little more of the system's actual functionality onto a component that was supposed to be optional. Eventually "optional" is a fiction — the software effectively doesn't work without the server, and nobody can point to the single decision that made that true.

This is not an argument against servers, and it is not "never use one." A server that provides genuine multi-peer coordination, or durability the local machine cannot itself provide, is doing real work that justifies the dependency, and the feature that needs it should say so plainly rather than pretending it could work standalone. The discipline is narrower and more specific: treat the local, embedded path as the floor every user gets regardless of network access or willingness to run infrastructure, and let server participation be a layer added on top for the users and features that specifically benefit from what a server can do that a local process cannot.

This connects to [[id:principle:single-source-shared-computation][single source for shared computation]] and [[id:principle:cross-platform-parity][cross-platform parity]] in the same way: all three are about refusing to let an unexamined default — the platform you tested on, the place logic happened to get written, the assumption that a server is always present — silently become a constraint nobody actually decided on. In each case, the corrective is the same habit: name the actual reason for a dependency or divergence explicitly, and if there isn't a real one, remove it rather than let it calcify.

#+title: Token-Efficiency Evidence for This KB's Structure
#+filetags: :molecular-notes:evidence:devpractice:

Whether an atomic, linked-note knowledge base is actually more token-efficient for an AI agent than one or a few large documents is a testable claim, not just a plausible-sounding one. This note reports a real measurement of this specific KB, run against the deployed knowledge base itself, and reproducible with `tools/measure-token-efficiency.sh`.

*Methodology*

For six representative queries an agent would plausibly ask of a development-practices KB (commit message format, ADR format, testing philosophy, AI-agent code annotations, periodic audit checklist, Makefile self-documentation), the single correct target note was identified and its exact on-disk size measured, then compared against two baselines: the full corpus (every note in the KB), and the smallest thematic hub-cluster that actually links to that note (a stand-in for "what if this were one merged category document instead of atomic notes" — computed automatically from the real link graph, not hand-picked).

*Results*

Across all six queries, fetching the correct single note cost 98.3–99.0% less than reading the entire corpus, and 90.1–95.2% less than reading the smallest relevant thematic cluster. In other words: the targeted note needed for a typical question is roughly 1.0–1.7% of the full KB's size, and still only about 5–10% of the size of even a modest, well-scoped category document covering the same topic area. These numbers move slightly as the KB grows (they were 98.0–98.7% / 86.8–93.5% at 70 notes, and improved rather than degraded by 85 notes) — re-run `tools/measure-token-efficiency.sh` after any substantial addition rather than treating these as fixed forever.

*Why this matters, and why it isn't a fluke*

This result is consistent with, and at the high end of, published precedent for atomic/linked-note retrieval architectures. A-MEM, an explicitly Zettelkasten-inspired agent-memory system built on atomic linked notes, reports 85–93% token reduction versus a monolithic-context baseline. Anthropic's own memory tool combined with context editing reports an 84% token-consumption reduction over a long agentic session. This KB's measured 98%+ reduction against a full-corpus baseline sits above both — plausible given this KB's notes are deliberately kept smaller and more single-purpose than a general-purpose memory system's stored context, at some cost in per-note self-containedness (see [[id:practice:when-to-create-a-new-node][when to create a new node]] for that tradeoff).

As a further cross-check, the same measurement tool — unmodified except for accepting a different KB directory — was run against an entirely independent, much larger molecular-notes KB (a different project's 236-file, 1,077-node built-in documentation corpus, 59 of those files holding a further sub-split of individual concept nodes, 724 more auto-generated directly from that project's own command and configuration-option registries rather than authored as prose), built separately and using a different internal linking convention. It showed the same order of magnitude: 98.7–99.5% reduction against the 236-file, ~235KB prose-documentation subset. Consistent results on two independently-built KBs of very different size and origin is stronger evidence than either measurement alone — it suggests the effect comes from the atomic-note architecture itself, not from something specific to this one KB's particular content or scale.

*Adversarial round — trying to break the claim, not just confirm it*

The same tool was then run against two more independent, real, unrelated knowledge bases specifically to look for holes, not to collect more confirming numbers: a large (2,345-file) general-purpose personal knowledge base spanning years of unrelated topics, and the working knowledge base of an active, real development project (46 files). Both lack this project's hub-note convention, so only the full-corpus comparison was available, not the stronger cluster-baseline comparison. Results: 99.97%+ ("100.0%" at one decimal place) reduction on the 2,345-file KB, and roughly 98.9–99.3% on the 46-file KB (three samples, computed by hand against the combined reference corpus since the relevant files spanned two directories the tool doesn't merge automatically).

Two genuine limitations came out of this round, not just more confirming data:

- *The "vs. full corpus" comparison weakens, not strengthens, as the corpus grows.* The 2,345-file KB's ~100% figure looks more impressive than this KB's own 98%, but is actually *weaker* evidence for the atomic-notes-specifically-help claim: in a large enough corpus, any single item is trivially tiny relative to the whole, regardless of whether the KB is well-structured or not. The measurements that actually support the claim are the two with a genuine cluster baseline (this KB and the 236-file manual) — comparing against a realistically-scoped alternative document, not an arbitrarily large unrelated denominator. A large raw-percentage number from an unstructured KB should not be read as stronger proof than a smaller percentage from a structured one; it may be measuring something closer to "big pile, small item" than "atomic notes help."
- *Query selection is circular across every measurement here, including the original ones.* Every query was written already knowing which note would answer it. This is a reasonable way to measure a KB's *structural* retrieval-size ceiling (the point of this note), but it doesn't test the harder, more realistic case: a query where the right note isn't obvious, or where several notes are plausible candidates. That gap is a real one, not yet closed by any measurement in this note.

The claim as stated at the top of this note — real, measured, atomic-note retrieval is dramatically smaller than reading a full corpus or a topically-scoped alternative, cross-validated with a genuine cluster baseline on two independently-built KBs — held up under this adversarial round. It should not be read as "this works equally well and for the same reasons on any knowledge base regardless of structure," which the two additional, unstructured-corpus measurements do not establish.

*Caveat — this measures the structural ceiling, not yet the delivered result*

This measurement assumes a search tool actually surfaces the correct target note for a given query. It does not itself validate that assumption. This note originally flagged two live tool-behavior gaps that could break that assumption: a missing scope-filtering parameter on the RAG-oriented search tool (letting results get diluted by unrelated federated knowledge bases), and a policy-check ordering issue that could block an explicitly-scoped search outright even when it was correctly scoped away from the problem. Both were filed as upstream issues.

*Re-validated, now that both fixes have landed.* Re-running the same six canonical queries plus several more, live, with the search tool's `scope` parameter set explicitly, against three separate federated knowledge bases (this KB, and two more real, independently-built ones registered on the same machine) turned up two distinct results, not one:

- *The scope-isolation fix is confirmed, cleanly, with no exceptions found.* Every one of roughly a dozen scoped queries run across all three knowledge bases returned results exclusively from the requested instance — zero cross-contamination from any other federated KB, including ones with much larger node counts. This closes the specific gap the two filed issues described.
- *A separate, previously-undetected ranking-quality gap remains, and re-validation surfaced it rather than closing it.* Even with scope correctly set, the RAG-oriented search tool failed to surface the correct target note at all, in the top few results, for roughly a third of this KB's own six canonical queries — including two that returned zero results outright — when queried with the same natural-language phrasing a person would actually type. Results improved markedly when the query used vocabulary closer to the target note's own title (e.g. "adversarial testing" instead of "what's the testing philosophy for this project"), but did not fully close the gap even then. The plain, non-RAG search tool performed somewhat better on the same queries in a smaller sample, though it wasn't exhaustively tested either. This is a genuine, separate limitation — not the same bug as the two that were fixed. Filed as a new upstream issue, distinct from the two above, once identified during this re-validation.

Net effect: the scope-safety half of the original caveat is resolved. The ranking-quality half is not, and this note now says so plainly rather than assuming the fix for one gap closed both. The numbers earlier in this note still represent this KB's *structural* efficiency ceiling; live delivered efficiency now matches that ceiling only when the query wording is chosen well, which is not yet guaranteed for an arbitrary natural-language question. A query-phrasing-robustness fix (or a documented mitigation, such as the calling agent retrying with title-vocabulary terms on an empty result) is the next real gap to close here, not a re-run of this same measurement.

*The ranking-quality gap generalizes — this isn't specific to this KB.* The same live, scoped, natural-language-query test was then repeated against the same two independent, unrelated, real knowledge bases used for the structural adversarial round above (not just re-run against this KB again), using generic technical topics plausible for each KB's own domain. One methodological check mattered here and is worth naming explicitly: before counting any zero-result query as evidence of a ranking failure, its target note's actual existence was independently confirmed (via a separate, broader keyword search) rather than assumed from this KB's own topic list. That check caught a real miscount — one candidate query, on the topic least native to one of the two other KBs (an infrastructure-migration project KB, not a software-testing-focused one), returned zero results because no on-topic note exists there at all, which is correct behavior, not a bug, and was excluded rather than counted. After that correction, the pattern still held on both other knowledge bases: a comparable fraction of natural-language queries with a *confirmed-existing* target failed to surface it in the top few results, including at least one further confirmed zero-result case (a topic verified to exist via keyword search but not found by natural-language phrasing). This is meaningfully stronger evidence for the *ranking-quality* gap than testing one KB alone, the same way testing the *structural* claim on multiple KBs earlier in this note was stronger than testing one: three independently-built, differently-structured, differently-sized knowledge bases all show the same order-of-magnitude shortfall on their confirmed-existing targets, which points at the ranking algorithm itself rather than something specific to this KB's note titles or tagging conventions.

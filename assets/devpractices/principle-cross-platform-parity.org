#+title: Cross-Platform Parity as a Constraint From the Start
#+filetags: :principle:architecture:devpractice:

If a system is meant to run on more than one platform, target, or environment, treat parity across those targets as a constraint present from the very first line of code — not a feature to reconcile once a second platform is added on top of code that was only ever exercised on the first. This applies to operating systems, but the same reasoning covers any multiplicity of targets a system must behave identically across: browsers, device form factors, deployment environments, or client runtimes. The specific instance of "platform" matters less than the discipline: assume from day one that whatever you're building will be run somewhere other than your own development machine, and verify it there, continuously, rather than at the end.

The failure mode when parity is an afterthought: a script, a path-resolution routine, or a tool invocation is written and tested only on the primary developer's machine, using conventions specific to that platform — a shell command that only exists on one OS, a directory-resolution helper that follows one platform's conventions and silently ignores the environment-variable overrides the project's own configuration system promises to honor, a path separator or line-ending assumption baked in implicitly. It works, ships, and is never touched again until someone on a different platform hits it — at which point it either fails loudly (the tolerable outcome) or, worse, silently no-ops or produces subtly wrong output that isn't noticed until much later, at which point the person debugging it has no reason to suspect a platform-specific code path, because nothing about the failure looks platform-specific from where they're standing.

The corrective has a few concrete habits. First, prefer portable, capability-gated logic over platform-name-gated logic: check "is this capability available" (does this command exist, does this environment variable resolve) rather than "am I on platform X," because capability checks degrade gracefully to new platforms and environments that weren't anticipated, while name checks silently fail closed or open depending on which branch is the default. Second, when a platform-specific tool is unavoidable, provide an explicit fallback chain (preferred tool, then a more universal one, then a documented absence) rather than assuming the preferred tool is always present. Third, when a system has a documented configuration contract (for example, "config and data directories follow a specific environment-variable-driven convention"), verify that contract holds identically on every supported platform — a convenience library that "mostly" does the right thing but follows a different, platform-native convention by default is a silent contract violation waiting to break automated tests or user expectations on exactly the platform nobody was testing against.

Finally, and most importantly: exercise every supported platform continuously, not periodically. A parity bug caught in continuous integration on every change is a two-line fix; the same bug discovered by a user three releases later, after several more platform-specific assumptions have piled on top of it, is a multi-day archaeology project. This is doubly true for anything touching paths, sockets, or shell invocations, since those are exactly the surfaces where platform conventions diverge most and where a bug is least likely to be caught by a purely logical, platform-agnostic test.

This principle is the cross-machine corollary of [[id:principle:single-source-shared-computation][single source for shared computation]] (shared logic that silently forks per platform is a parity bug in waiting) and of [[id:principle:downstream-impact-checklist][the downstream-impact checklist]] (verify the change on every supported target, not just the one in front of you).

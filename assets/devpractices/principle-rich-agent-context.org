#+title: Give an AI Agent Structured Context, Not Just Raw Text
#+filetags: :principle:ai-collaboration:devpractice:

An AI agent reasons far more reliably from structured, tool-derived signals than from raw unstructured text it has to re-derive structure from itself. A type checker already knows the type of an expression; a debugger already knows the call stack and the value of every variable in scope; a linter already knows exactly which line violates which rule and why. When a system exposes these signals to an agent directly — as typed, addressable facts rather than as prose the agent must re-read and re-infer from source text — the agent spends its reasoning budget on the actual problem instead of on reconstructing information the system already had on hand.

The general shape of the principle: don't make the agent reconstruct from raw text what a structured tool in the system already knows. This generalizes past any single integration. It applies to type information, symbol references, runtime call stacks and variable state, diagnostic output, build errors, test results — any case where some component of the system already computes a structured answer to a question the agent needs answered. If that structured answer exists somewhere in the system, piping it to the agent as structured data is strictly better than requiring the agent to grep source files and pattern-match its way to the same conclusion.

The failure mode when this is ignored: a coding agent is given file read access and a shell, but no access to the language server's understanding of the code, no access to a debugger's live state, no access to structured diagnostics. To find every caller of a function, the agent greps for the function's name across the repository — and gets false positives from string literals, comments, and shadowed identifiers in unrelated scopes, along with false negatives from call sites reached through an alias, a trait dispatch, or a macro expansion that plain text search can't see. To understand why a program crashed, the agent asks the user to paste a stack trace instead of being able to inspect live frames and variable values itself. Each of these tasks is one a purpose-built tool already solves precisely, but the agent is forced to approximate the tool's answer from weaker signal, produces a plausible-looking but wrong answer, and the mistake isn't caught until the change based on that wrong answer breaks something the agent had no way of knowing was connected.

The corrective is to treat "what does the agent see" as a first-class design question alongside "what can the agent do." If a system already builds structured tooling for its human users — a type checker, a symbol index, a debugger, a linter — expose that same tooling's output to the agent as part of its available context or as callable tools, rather than only exposing a text-editing surface and expecting the agent to rebuild the tooling's insight from scratch by reading. Where no such structured tool exists yet, building one benefits every consumer, human and agent alike, which is a strong argument for prioritizing it over a narrower agent-only workaround.

This is a specialization of [[id:principle:ai-as-peer-actor][treating an AI agent as a peer actor]]: a peer actor gets the same rich, structured view of the system that a well-tooled human user gets, not a degraded text-only view. It also has a narrower, comment-level analogue in [[id:practice:caution-annotations][caution annotations]] — a caution annotation is one specific mechanism for handing an agent a structured signal (an explicit invariant warning) that would otherwise have to be re-derived, error-prone, from reading code alone.

#+title: Single Source for Shared Computation
#+filetags: :principle:architecture:devpractice:

When the same logic is needed across multiple backends, platforms, code paths, or variants of a system, it should live in exactly one place that all of them call into — never as two or more independent implementations that happen to compute the same thing today. This applies to layout math, data transformation, validation rules, formatting logic, business rules — any computation whose result two or more parts of the system depend on. The specific mechanism (a shared library, a common module, a base class, a pure function extracted to a shared crate/package) matters less than the invariant: one definition, many callers.

Two independent implementations of the same computation will drift apart over time, even when both start out byte-for-byte equivalent and both are maintained by people acting in good faith. The mechanism is mundane and nearly guaranteed: a bug is found and fixed in implementation A, because that's the one the reporting user happened to be exercising — and the fix never makes it to implementation B, because nobody remembered, or nobody knew, that B needed the same fix. A new edge case is handled in B during an unrelated feature addition, and A never receives it either. Months later, the two paths produce silently different output for the same logical input, and nobody notices until a user files a confusing bug report about inconsistent behavior between two parts of the same product that were supposed to behave identically — at which point diagnosing the discrepancy requires diffing two codebases that were never meant to diverge in the first place.

The corrective is structural, not a matter of discipline: extract the shared computation into one module the first time it's needed in more than one place, not after the second implementation has already been written and has already started to drift. If you notice you're about to write logic that closely resembles something already in another part of the codebase, that's the signal to stop and extract a shared function rather than writing a second, superficially different version. Backend-specific or platform-specific code should be reduced to the minimum that genuinely differs — the actual platform API calls, the actual rendering primitives — while everything upstream of that (what to compute, not how to paint it) is computed once and handed to each backend as data.

This is not purely an efficiency argument (though duplicated logic is wasted effort); it's a correctness argument. A system with duplicated computation has, by construction, an implicit and unenforced invariant — "these two implementations must stay equivalent" — that nothing in the codebase checks or enforces, and unenforced invariants decay. Making the invariant impossible to violate (there is only one implementation, so there is nothing to keep in sync) is strictly better than documenting the invariant and hoping.

This principle underlies [[id:principle:modular-boundaries][modular boundaries]] — a well-bounded module is precisely the extraction point shared computation needs — and interacts with [[id:principle:cross-platform-parity][cross-platform parity]], since platform divergence is one of the most common and highest-cost places this principle gets violated: a computation reimplemented per-platform instead of shared is a parity bug waiting to happen the next time one platform's implementation is touched and the other isn't.

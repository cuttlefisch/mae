#+title: Fix the Root Cause, Not the Symptom
#+filetags: :principle:process:devpractice:

When a bug or unwanted behavior surfaces, the correct fix addresses why it happens, not merely makes the immediate symptom stop being visible. A kludge — a special case that catches the bad output after the fact and corrects it, a retry loop papering over an operation that fails for a reason nobody investigated, a defensive null-check added at the call site instead of fixing the function that shouldn't be returning null in the first place — resolves the ticket but leaves the actual defect fully intact, waiting to resurface somewhere else.

A workaround compounds technical debt and often hides the real bug for someone else to rediscover later, at higher cost. The mechanism is straightforward: the underlying defect doesn't go away when it's worked around, it just becomes harder to find, because the visible symptom that would have led an investigator to it is now suppressed. The next person who hits the same underlying defect — from a different call site, through a different code path, under a slightly different set of conditions — sees a different, seemingly unrelated symptom, with no obvious link back to the first occurrence or its workaround. They re-diagnose from scratch, possibly add their own workaround for their own symptom, and the codebase accumulates a second patch over the same unaddressed root cause. Each additional layer makes the eventual real fix more expensive, because by the time someone does trace it back to the actual defect, they now also have to understand and safely remove however many workarounds were built on top of it in the meantime, some of which other code may have come to depend on.

The corrective discipline is to keep asking "why" past the first plausible answer until you reach something that, if fixed, would make the workaround itself unnecessary — not just something that, if worked around, would make this instance of the symptom go away. If a function is returning an unexpected null, the root-cause question isn't "how do I handle null at this call site" but "why is this function producing null when its contract says it shouldn't, and is every other caller of this function exposed to the same defect right now, silently." If an operation intermittently fails and a retry loop makes the failures stop being visible, the root-cause question is what is actually causing the intermittent failure — a race condition, a resource limit, a timeout too short for real-world latency — because a retry loop only ever converts a bug into a rarer, harder-to-reproduce bug, it never removes it.

This doesn't mean every fix must resolve an entire feature area in one pass — sometimes the true root cause is large and the immediate fix is necessarily a bounded first step. The discipline in that case is to make the bounded scope explicit and tracked (see [[id:principle:no-deferred-bugs][no deferred bugs]] and [[id:principle:bugs-are-drift-signals][bugs are drift signals]]) rather than letting a partial fix be silently mistaken for a complete one. What distinguishes a legitimate bounded fix from a kludge is that the bounded fix is a genuine, documented subset of the real solution moving in the right direction, while a kludge is orthogonal to the real solution — it makes the symptom disappear without making the underlying system any closer to correct.

See [[id:principle:no-deferred-bugs][no deferred bugs]] for what to do when the real fix genuinely can't happen right now, and [[id:principle:downstream-impact-checklist][the downstream-impact checklist]] for verifying a root-cause fix doesn't leave sibling code paths with the identical unaddressed defect.

#+title: Tagged Flag Comments (BUG/KLUDGE/PERF/DOGFOOD/FIXME)
#+filetags: :code-annotation:devpractice:

Tagged inline comments mark known problems directly at the point in the code where they live, using a small fixed vocabulary so they are greppable across a whole codebase by convention rather than by memory:

- **BUG:** — a confirmed incorrect behavior that hasn't been fixed yet, distinct from a TODO (which marks unfinished, not incorrect, work).
- **KLUDGE:** — code that works but was written as a shortcut, workaround, or stopgap; it is correct today but architecturally uncomfortable.
- **PERF:** — a known performance cost that was accepted deliberately, usually because fixing it properly was out of scope at the time.
- **DOGFOOD:** — behavior that hasn't been verified or measured under real usage/data yet, only under synthetic conditions (a test fixture, a small local dataset, a happy-path manual check). Distinct from BUG (no known incorrect behavior, just no real-world confidence yet) and worth its own tag rather than folding into a generic TODO, because "works in the test suite" and "verified against real usage" are different claims that get silently conflated otherwise.
- **FIXME:** — something that must change before the surrounding code can be considered done, often narrower in scope than BUG.

Each tag requires two things to be useful rather than noise: a one-line explanation of *why* the problem exists (not just that it exists — "why" is what lets a future reader judge urgency), and a reference to a tracked issue number. A flag comment with no issue reference is a comment nobody owns and nobody will revisit; it decays into permanent background noise that readers learn to ignore, which defeats the entire purpose of tagging.

```
// KLUDGE(#412): skip the cache-invalidation pass here because the cache
// key doesn't yet encode schema version — remove once #412 lands.

// DOGFOOD(#530): batch size tuned against a synthetic 10K-row fixture;
// not yet verified against a real production-sized dataset.
```

Beyond the inline comment, maintain a project-level index of flagged locations — generated by grepping the fixed tag vocabulary across the tree, not hand-maintained, and named consistently so it's discoverable on its own (a file like `docs/CODE_REVIEW_FLAGS.md`, kept as a running, regenerable index rather than a one-time snapshot) — so the full set of known rough edges is visible in one place (e.g. as part of a periodic audit) rather than only discoverable by stumbling onto them while reading unrelated code. This is what makes the convention scale: a single KLUDGE comment is a note to self, but a hundred of them indexed together are a map of a codebase's actual condition.

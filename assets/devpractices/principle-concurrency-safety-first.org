#+title: Design for Concurrency From Day One
#+filetags: :principle:architecture:devpractice:

Concurrent and shared access is a foundational design constraint, not a feature to bolt on once the system is popular enough to need it. Every piece of mutable state in a system will eventually be observed or modified from more than one execution context — a background thread, a second client, a plugin, an async task — even if the first version only has one caller. Deciding up front what a shared-access model looks like (ownership rules, locking discipline, message-passing boundaries, or a language's type system enforcing exclusivity) is a design decision with a narrow window: it is cheap before any code depends on the old single-threaded assumptions, and it gets more expensive every month afterward.

Retrofitting concurrency into a codebase that was not designed for it is disproportionately expensive compared to designing for it upfront, and the retrofit is usually incomplete. The failure mode looks like this: a system starts single-threaded because it's simpler to reason about. Years and thousands of commits later, the demand for concurrent access becomes undeniable — multiple users, multiple background jobs, a UI that must stay responsive while work happens elsewhere. A retrofit project starts. It touches every subsystem that holds mutable state, because the assumption of exclusive access was never localized to one place; it was implicit everywhere. The project drags on for years, spans multiple false starts under different names, and even after "shipping" leaves parts of the system still assuming single-threaded access, because nobody could enumerate every place the assumption was baked in.

The corrective is architectural, not tactical: pick a concurrency model before writing the first stateful subsystem, and make that model impossible to accidentally violate rather than merely documented. A type system that refuses to compile code sharing unsynchronized mutable state is far more durable than a code comment saying "don't call this from two threads." Message-passing or actor-style isolation, where state is only ever touched by one owner and mutated via messages, sidesteps the retrofit problem entirely because there is no shared-mutable-state invariant to have silently violated in the first place. Whichever model is chosen, it should be enforced structurally — by the compiler, the runtime, or a lint — not by convention alone, because convention-only invariants are exactly what erodes first under deadline pressure.

This principle compounds with keeping module boundaries small (see [[id:principle:modular-boundaries][prefer modular boundaries over a monolithic core]]): a system built from many small, independently-owned modules with narrow interfaces is far easier to reason about under concurrent access than one enormous file where every function can reach into every piece of shared state. Concurrency safety and modularity are not separate concerns — a monolith with no internal boundaries has no natural seams at which to introduce safe concurrent access later, which is part of why retrofits on such systems take years rather than weeks.

Practically, this means: when starting a new service, library, or subsystem, name the concurrency model in the design document before writing the first stateful line of code. When reviewing a proposed change, ask "what happens if this runs from two contexts at once?" even if today there is only one caller — today's single caller is next year's constraint nobody remembers arguing for. Treat "we'll add locking later" as a decision to pay a much larger bill later, not a deferral of cost.

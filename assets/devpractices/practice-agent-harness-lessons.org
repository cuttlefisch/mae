#+title: Lessons for Building Reliable Agent Harnesses
#+filetags: :ai-collaboration:devpractice:

Building the tooling that drives an AI agent — the harness that sends it prompts, parses its responses, and dispatches its tool calls — surfaces a distinct set of reliability problems from the ones the agent's underlying model has. These recur across projects and are worth designing for up front rather than discovering through production failures:

- **Validate and rescue-parse model responses; never trust them blindly.** A model response that is supposed to be structured (JSON, a specific tool-call shape, a fenced code block) will occasionally be malformed, truncated, or wrapped in extra prose. The harness must validate the shape before acting on it, and where possible attempt a rescue parse (strip wrapping text, repair common formatting slips) rather than either crashing or silently proceeding on garbage. Treat "the model said X" and "X is a validated, well-formed response" as two different claims.
- **Give targeted retry nudges, not generic retries.** When a call fails or produces an unusable response, a bare "try again" retry reproduces the same failure at a similar rate, because it gives the model no new information about what went wrong. A retry that names the specific problem ("your last response was missing the required `path` field" rather than "that didn't work") measurably improves the odds of the next attempt succeeding, because it turns the retry into new information rather than a repeated coin flip.
- **Enforce expected step sequencing.** Agentic workflows often have an implicit protocol — a setup call before an action call, an acknowledgment before a destructive operation — and a harness that lets the model skip or reorder steps is trusting the model to enforce its own protocol correctly, which it will not always do. Enforce the sequence in the harness itself: reject or short-circuit calls that arrive out of order rather than accepting them and hoping downstream state tolerates it.
- **Stay aware of context-compaction effects on long sessions.** As a session grows, context gets summarized, truncated, or otherwise compacted to fit budget constraints. Instructions, constraints, or earlier decisions that lived only in now-compacted context can silently stop influencing the model's behavior partway through a long session. Design the harness to re-surface load-bearing constraints (permissions, scope boundaries, standing instructions) near the point of use rather than relying on them persisting from early in the conversation, and treat behavior drift over a long session as a compaction symptom to investigate, not just a model quirk.

These are harness-engineering concerns, distinct from prompt quality or model capability — a well-designed harness makes a mediocre model behave reliably, and a poorly designed one lets even a capable model produce unreliable results.

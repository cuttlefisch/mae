#+title: Guidance, Skill, or Deterministic Code
#+filetags: :ai-collaboration:process:devpractice:

Not every practice belongs in the same form. A convention can be written as prose an AI agent reads and reasons over, packaged as a parameterized skill/procedure the agent follows while still exercising judgment within known bounds, or codified as an exact deterministic script that guarantees an outcome without depending on the agent's compliance at all. Picking the wrong form for a given practice is a common, avoidable failure mode — either wasting effort building rigid tooling around a genuinely context-dependent judgment call, or trusting prose to reliably prevent a violation that is one distracted moment away from happening.

The deciding factor is the task's degrees of freedom — how much legitimate variation is acceptable, and how costly a deviation is:

- **High freedom → prose.** Multiple approaches are valid, the right call depends on context that can't be fully enumerated in advance, and a human or agent needs the full picture to decide well. Most architectural judgment calls, code review feedback, and "how should I think about this" guidance belongs here.
- **Medium freedom → a parameterized skill.** A preferred pattern exists, and some variation around it is fine — the shape is known, the specifics adapt to the situation. A checklist with fill-in fields, a template with placeholders, a multi-step workflow with branch points, all fit here.
- **Low freedom → an exact deterministic script.** The operation is fragile, a specific sequence must be followed exactly, and the cost of a silent deviation is high. This is the "narrow bridge with cliffs on both sides" case: there is no room for interpretation, so don't leave room for interpretation. A lint check, a schema validator, a CI gate, a migration script — anything where "close enough" isn't actually close enough.

A concrete instance of this KB getting the level wrong, caught in the KB's own development: the mandatory rule that every internal link must use the explicit `id:`-prefixed form (see [[id:practice:node-linking][node linking]]) was first shipped as prose guidance alone — a written instruction telling every note author "always use this form, never a bare one." That instruction was followed almost everywhere, but not everywhere: one note ended up with a bare-prefix link inside an illustrative example, and a first-draft lint check missed it too (a whole-line check, rather than a per-match one, let a line containing both a correct and an incorrect example slip through). The fix was not "write a stronger sentence" — it was a script (`check-links.sh`) that mechanically verifies every internal link, every time, with no dependence on anyone remembering the rule correctly under load. This is exactly the low-freedom case: a link's form is either right or wrong, there is no legitimate variation, and the cost of a silently broken link is a permanently unreachable note. Prose was the wrong tool for that specific job — not because prose is weak in general, but because this particular rule had zero degrees of freedom.

The general lesson generalizes past this one example: if a violation is mechanically checkable and the cost of it slipping through silently is high, write the check — don't ask for compliance you can verify instead. If the task is well-defined but still needs adaptation to context, a skill is the right shape. Reserve pure prose for genuine judgment calls, where a script would either be impossible to write correctly or would strip out exactly the contextual reasoning the task actually needs. See [[id:practice:node-linking][node linking]] for the worked example this note is built from, and [[id:hub:molecular-notes-methodology][molecular notes methodology]] for how this KB is itself organized around that same distinction — prose atoms for judgment calls, and this KB's own tooling (`check-links.sh`, `measure-token-efficiency.sh`) for the parts that shouldn't depend on anyone remembering to check.

#+title: Prefer Modular Boundaries Over a Monolithic Core
#+filetags: :principle:architecture:devpractice:

Clear module boundaries with single, narrow responsibilities beat letting any one file or component grow to absorb an ever-widening share of a system's logic. A module boundary is a promise: code inside it owns a well-defined piece of behavior and exposes a deliberate interface to the rest of the system. Every time an unrelated concern gets folded into an existing "convenient" file instead of getting its own module, that promise erodes a little, and the cost of the erosion is nonlinear — a file twice as large is not twice as hard to work in, it's often an order of magnitude harder, because the number of interactions between its parts grows combinatorially, not linearly.

A monolithic core file becomes a maintenance bottleneck and a single point of failure for everyone working near it. The concrete failure mode: one file — often the oldest, most "central" one in the system — accumulates display logic, business logic, and edge-case handling for every feature that ever needed to touch that area, because it was always the path of least resistance to add "just one more case" to the file that already handles similar things. Over years, it grows to tens of thousands of lines. It becomes the single most bug-prone file in the codebase, because it has the highest change frequency and the highest coupling: touching any one part risks unintended interaction with a dozen others. It also becomes a bus-factor risk — only a small number of people fully understand it, so nearly every substantial change routes through them, and the whole team's throughput is bottlenecked on their availability.

The corrective is to extract a new module the moment a piece of logic has a coherent, nameable responsibility distinct from its neighbors — not after the file has already become unmanageable. A useful heuristic: if you can describe what a chunk of code does in one sentence without using "and," it's a candidate for its own module with its own interface. Boundaries should be drawn along responsibility, not convenience — the fact that two pieces of logic happen to touch the same data structure is not sufficient reason to co-locate them if they serve genuinely different purposes (e.g., computing a value versus rendering it, or parsing input versus validating business rules on it).

Modular boundaries also enable distributed ownership: when responsibility is legible and localized, more people can work on a system concurrently without stepping on each other, and no single person becomes a structural dependency for an entire area of functionality. This is the direct organizational payoff of the technical discipline — bus-factor problems in mature codebases are rarely solved by hiring more people onto an already-monolithic file; they're solved by having drawn boundaries early enough that new people can own a module without first reverse-engineering an entire subsystem.

This principle pairs with keeping shared computation in exactly one place (see [[id:principle:single-source-shared-computation][single source for shared computation]]): good modular boundaries are what make it possible to share logic without duplicating it, since a well-bounded module is precisely the thing multiple call sites can depend on instead of each reimplementing a piece of it inline. When reviewing a change, treat "this file is already 3000 lines, might as well add here" as a signal to stop and extract, not a justification to continue.
